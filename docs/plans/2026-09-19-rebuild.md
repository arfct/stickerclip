# Stickerclip 2: rebuild as an app — plan

**Date:** 2026-09-19
**Status:** draft for review

## What we're building

Stickerclip today is a Messages-only extension from 2022: one 850-line UIKit
view controller, frame-positioned storyboard views reparented into collection
cells, and a sticker library that lives inside the extension's own container.
It broke on iOS 26 and the shape of the code is why.

The rebuild is a proper iOS app with the Messages extension as one surface:

1. **An app** that holds your sticker library — browse, add, edit, delete, and
   see what's synced.
2. **A Messages extension** that shows the same library and lets you paste a
   new sticker in place.
3. **A share extension** so "Save to Stickerclip" appears in every share sheet.
4. **iCloud sync** so the library follows you across devices.

Same product idea — the clipboard becomes a sticker — but adding from Photos,
Files, the share sheet, or drag and drop, not paste alone.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Minimum OS | **iOS 18.0** | N-2. Everything the build needs (`@Observable`, SwiftData-free file store, `PasteButton`, `PhotosPicker`, `Transferable`) is iOS 16–17. Built against the iOS 27 SDK, Liquid Glass applies automatically on iOS 26+, so targeting 18 costs nothing on new devices and keeps the 2024–25 cohort. |
| Project | **XcodeGen `project.yml`** | Matches `minder` and `shareware`. Generated `.xcodeproj` is git-ignored. XcodeGen accepts JSON too; YAML keeps the repos consistent. |
| Team | **artifact, `TVA9Z8LD95`**, automatic signing | The blacktree team is PLA-blocked. See *Identity* — this has product consequences. |
| UI | **SwiftUI** everywhere; UIKit only where Messages requires it | `MSMessagesAppViewController` is UIKit. It hosts one `UIHostingController`. Nothing else in the project is UIKit. |
| Shared code | **`StickerKit`** local Swift package | Model, store, renderer, importer, sync. Three targets depend on it; the tests live there. |
| Sticker storage | **Files** in an App Group container, mirrored to **iCloud Drive** | A sticker *is* a file and Messages consumes a file URL. See *Storage and sync*. |
| Language mode | **Swift 6**, strict concurrency | New code, no legacy to appease. `@MainActor` UI, `Sendable` models, `actor` around the store. |

## Identity

The App Store record for `com.blacktree.stickerclip` has already been
transferred to the artifact team, so the rebuild ships as an **upgrade** to the
existing app: same bundle ID, same listing, same users.

That decides two things. The Messages extension keeps its existing ID,
`com.blacktree.stickerclip.MessagesExtension`, so the new extension lands in
the **same container** the old one wrote to — the migrator reads the old
`Documents` folder in place, no cross-container copying. And the shared
identifiers hang off the existing prefix:

```
App:            com.blacktree.stickerclip                     (existing)
Messages:       com.blacktree.stickerclip.MessagesExtension   (existing)
Share:          com.blacktree.stickerclip.share
App Group:      group.com.blacktree.stickerclip
iCloud:         iCloud.app.stickerclip                        (existing, see below)
```

The old iCloud container `iCloud.app.stickerclip` moved with the app in the
transfer — P0 confirmed it provisions under the artifact team. It was never
populated (sync was disabled in code), so reusing it costs nothing.

**P0 finding:** the transfer moved the app's App ID but not the extension's.
`com.blacktree.stickerclip.MessagesExtension` is a separate App ID and stayed
on the blacktree team, so the artifact team cannot register it until it is
removed there (developer.apple.com → Identifiers, as team `A7X888RRVJ`).
Renaming the extension would sign immediately but a new extension ID means a
new container, and iOS deletes the old one on upgrade — existing users would
lose their stickers. So the ID is being freed rather than replaced.

Every identifier is defined once at the top of `project.yml`.

## Storage and sync

### Why files, not a database

Three options were on the table:

- **iCloud Drive** — the sticker files live in the ubiquity container's
  `Documents`, iCloud syncs them, `NSMetadataQuery` reports changes.
- **SwiftData + CloudKit** — records with external-storage image data, in the
  App Group store, `cloudKitDatabase: .automatic`.
- **CKSyncEngine** with files in the App Group and `CKAsset` records.

Files win for this product. `MSSticker` needs a file URL, so a database would
have to export a file cache anyway. Stickers are write-once — an edit produces
a new file — so there are no merge conflicts to resolve. And a folder of PNGs
in iCloud Drive is visible in the Files app, which is a feature, not a
side-effect: issue #5 is literally "store stickers in iCloud".

SwiftData + CloudKit was the "modern" pitch but carries real costs here: every
attribute optional, no unique constraints, sync you can't observe from an
extension, and the file cache on top. Not worth it for a list of images.

### Layout

```
<container>/Stickers/
  2026-09-19T08-05-11Z-a1b2c3d4-border-408.png
  2026-09-19T08-07-42Z-e5f6a7b8-192.gif
```

`<container>` is the iCloud ubiquity container's `Documents` when iCloud is
available, else the App Group container's `Library/Application Support`. Both
targets resolve the same URL through `StickerLibrary.location`.

Metadata stays in the filename, as today, but sortable and collision-free:
creation timestamp, a short random ID, optional `border`, and the size
variant. No sidecar JSON — nothing to fall out of sync with the file.

### Behaviour

- **A ubiquity container cannot be read with plain `FileManager` calls.**
  Found on device in P2: `contentsOfDirectory` on the container's `Documents`
  fails with `NSCocoaErrorDomain` 256 over `NSPOSIXErrorDomain` 11, *Resource
  deadlock avoided*. Reads and writes go through `NSFileCoordinator`, and
  enumeration through `NSMetadataQuery` — the file-presenter contract, not an
  optimisation. `createDirectory` is no guide here: it succeeds on a container
  that then refuses to be listed, so P5 must prove the container by listing
  it, not by creating the folder.
  Until P5 lands, `LibraryLocation.resolve(preferringCloud:)` defaults to
  false and the library is local, so every other surface can be built against
  a store that works.
- **Placeholders.** iCloud items that haven't downloaded yet are shown with a
  progress state and `startDownloadingUbiquitousItem` is called on appearance.
  The extension does this too, so a sticker made on the iPad appears on the
  phone.
- **Change notification.** One `NSMetadataQuery` per process, wrapped in an
  `AsyncStream`. The library is an `@Observable` snapshot that the query
  updates on the main actor.
- **Signed-out fallback.** No iCloud account → local App Group store, same
  layout. When an account appears, local files are moved into the container
  once. The UI shows which mode is active.
- **Deletion** removes the file; iCloud propagates it.
- **Nothing is force-unwrapped.** Files that don't decode are skipped and
  surfaced in a diagnostic list, never crashed on. The old `try!` on every file
  in `Documents` is a design defect we are removing, not porting.

### Migration from the old extension

On first launch of either target: if the Messages extension's own container
has files in `Documents` — where the old app kept them — copy them into the
library with new names, verify each decodes, then remove the originals.
Idempotent and resumable. The app can't reach that container directly, so the
migrator runs inside the extension and the app just shows the result.

## Adding stickers

One `StickerImporter` in `StickerKit` turns any input into a `StickerSource`
and hands it to the renderer. The surfaces just feed it.

| Source | Where | API |
|---|---|---|
| Paste | App and Messages | `PasteButton` (SwiftUI); the extension's hosting controller declares `pasteConfiguration` and implements `paste(itemProviders:)` as a **pure** handler — `canPaste` never touches UI |
| Photos | App | `PhotosPicker`, multiple selection |
| Files | App | `.fileImporter` for `UTType.image`, multiple |
| Share sheet | Everywhere | Share extension accepting `public.image` and `public.url` |
| Drag and drop | App, iPad and iPhone | `.dropDestination(for: StickerSource.self)` via `Transferable` |
| Text | App and Messages | Short text becomes a large-type sticker, as today |
| URL | Any of the above | Fetched with `URLSession`, content type checked, rejected unless it decodes as an image |

The URL row matters more than it looks. Copying an image in Safari often puts a
`public.url` on the clipboard rather than image data — that was the "some
images fail" report during triage. Fetching URLs fixes the most common failure
in the old app, and the share extension gives Safari users a path that always
works.

### Renderer

Ported from the existing pipeline, in `StickerKit`, with tests:

- Fit within the sticker envelope: 300–618 pt square, default 408.
- Optional white stroke border and soft shadow (`showBorder` today).
- PNG when transparent, JPEG otherwise; ≤ 500 KB or step down a size.
- **Animated GIF and APNG pass through unchanged** when already within limits.
  The old code decoded through `UIImage` and flattened them to one frame.
- Reuse original bytes when the source is already within limits (existing
  optimisation, now without the `try` that could sink the whole paste).

## Surfaces

### App

- Library grid, newest first, with multi-select for delete and share.
- Add menu: Paste, Photos, Files. Drop target over the whole grid.
- Sticker detail: preview at real size, border toggle, size stepper,
  re-render, share, delete.
- Status: iCloud on/off, items still downloading, files that failed to decode.
- Empty state teaches the three ways in. This replaces the old instruction
  paragraph that had nothing to paste into.

### Messages extension

- `MSMessagesAppViewController` → `UIHostingController` → SwiftUI.
- **Compact:** a paste row and the most recent stickers.
- **Expanded:** the full grid with select and delete.
- Stickers are shown through `MSStickerView` wrapped in `UIViewRepresentable`
  so peel-to-drag and tap-to-insert behave natively. The system
  `MSStickerBrowserViewController` is the fallback if the wrapper fights the
  hosting controller; the old app moved off it deliberately, so this is worth a
  spike in P2 rather than an assumption.
- Reads the same library; no state of its own.

### Share extension

- Accepts one or more images or a URL.
- Renders through `StickerImporter` and saves. Shows the result for a moment,
  then dismisses.
- Compact SwiftUI UI in a `UIHostingController`; nothing else.

## Decomposition

| | Piece | Delivers | Depends on |
|---|---|---|---|
| **P0** | Scaffold | `project.yml`, three targets, `StickerKit` skeleton, App Group, iCloud entitlements, `scripts/`, builds and installs to the phone | — |
| **P1** | StickerKit | Model, file store with filename codec, renderer, importer, tests | P0 |
| **P2** | Messages | Hosted SwiftUI, paste, grid, peel/drag spike | P1 |
| **P3** | App | Library, add from Photos/Files/paste/drop, detail, delete | P1 |
| **P4** | Share extension | Save from any share sheet, incl. URLs | P1 |
| **P5** | iCloud | Ubiquity store, metadata query stream, placeholders, signed-out fallback, one-time local→cloud move, migration from the old container | P1 |
| **P6** | Release | Identity decision, PLA, TestFlight, store assets, site update | P2–P5 |

P2, P3 and P4 are independent once P1 lands. P5 touches the store P1 defines
but nothing above it, so it can run alongside P3/P4. **P2 ships to the phone
first** — it is the piece users are missing today, and it exercises the store
in the most constrained process.

## Verification

### Automated — `StickerKitTests`

- Filename codec round-trips every field; sorts by creation time.
- Renderer: every input lands in the envelope, under 500 KB, transparent →
  PNG, opaque → JPEG, GIF passes through, border adds the expected margin.
- Importer: synthetic `NSItemProvider`s for image data, file URLs, remote URLs
  (stubbed session), text, and an empty provider list — the last must be a
  no-op, not an error.
- Store: add/list/delete on a temp directory; a corrupt file is skipped and
  reported, never thrown.
- Migrator: old-layout fixture → new layout, idempotent on re-run.

### On device — `scripts/`

The triage loop that found the real bugs, made repeatable:

| Script | Does |
|---|---|
| `generate.sh` | `xcodegen generate` |
| `device-install.sh [name]` | build for the connected device, install, print bundle IDs |
| `device-pasteboard.sh <image>` | put an image on the phone's clipboard via `devicectl` |
| `device-library.sh` | list or pull the App Group container |
| `device-screenshot.sh` | capture the phone |

Two facts from triage that shape testing: `devicectl` cannot launch or attach
to a Messages extension, so extension diagnostics go to a file in the App
Group container and are pulled with `device-library.sh`; and `canPaste` is
polled by the system every couple of seconds while the paste control is on
screen, so any side effect there runs constantly.

## Why the old code broke — designed out, not patched

Recorded so the rebuild doesn't reproduce them.

- **`canPaste` rewrote the UI.** The system polls it; on iOS 26 it is polled
  with an empty array, so the old code hid its own editor — and the paste
  control inside it — on every poll. This was issue #6. → Paste handlers are
  pure; `pasteConfiguration` is declared.
- **The root view was a placeholder.** The real UI was swapped in from
  `didBecomeActive`. Any earlier layout showed an empty white view. This is a
  strong candidate for issue #2. → One hosting controller, installed in
  `loadView`.
- **Cells measured themselves.** The editor cell's size came from a view that
  was resized to the cell. → SwiftUI layout; no frame math.
- **The library lived in the extension's container.** Nothing else could read
  it and iCloud was bolted on afterwards. → App Group + iCloud from the start.
- **Every file was `try!`-decoded.** One stray file in `Documents` crashed the
  extension. → Skip and report.
- **One `try` aborted the paste.** Reading original bytes, an optimisation,
  sat in the same `do` as sticker creation. → Optional steps are optional.

## Open questions

1. **Text stickers in the share extension?** Sharing text from Safari could make
   a text sticker; probably yes, cheap once the importer exists.
2. **macOS / iPad?** `supportedDestinations` makes iPad free; macOS Messages
   has no extension point, so the app would stand alone there. Not in scope for
   P0–P6; the package layout doesn't preclude it.
